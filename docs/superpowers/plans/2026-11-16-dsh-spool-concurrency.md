# DSH spool 多进程修复计划

当前 JSONL 实现为每个实例缓存整份记录，确认后重写文件；两个进程共享目录会
覆盖彼此尚未确认的记录。生产切换前仍必须为每个实例配置独立 `persistenceDir`。

## 方案与边界

优先实现基于 SQLite 事务的 spool。此机实际运行的 DSH 使用 Node v24.16.0，
已验证内置 `node:sqlite` 可加载；其他目标机须单独检查运行时，不据此假定其
兼容。队列只能放在支持 SQLite 锁语义的本地文件系统；网络文件系统需单独验证。
保留 JSONL 作为旧版格式，迁移必须先停止所有旧版写者，保留原始文件并验证导入。

备选是稳定锁文件上的内核 `flock`，但 Node 标准库没有该 API，外部持锁进程会
引入生命周期和平台依赖；而且所有读取、容量检查、追加和改写都必须在同一把锁
下重新加载，不能只给现有 rewrite 加锁。`mkdir` 锁也不能仅靠 PID 或时间回收，
否则会在 PID 复用或长暂停时产生并发写者。

## 实施和验收

1. 编写独立 SQLite spool 实现，事务内完成去重、容量检查、入队、确认删除和
   永久失败标记；限定忙等待时间，避免阻塞宿主。确认删除使用记录代次以防 ABA。
2. 先测试双进程同时入队、容量竞争、确认时并发追加、相同 key 去重、永久失败
   状态以及数据库不可写或繁忙时的失败关闭。投递只承诺至少一次，继续依赖服务端
   `(session_id, message_id)` 幂等；不能在网络发送期间持有数据库写事务。
3. 模拟持有事务的进程 SIGKILL，验证另一进程取得锁、已提交数据保留、未提交数据
   回滚；验证确认后删除前崩溃时可安全重放。
4. 提供离线 JSONL 导入：停止旧写者、校验完整 JSONL、事务导入并记录迁移标记，
   保留原文件；测试中途崩溃后重试、损坏数据、永久失败记录和重复导入。
5. 接入可配置的后端并检查宿主 Node 版本；在不支持 `node:sqlite` 时明确失败，
   不回退到共享 JSONL。完成双进程集成测试和真实 DSH 会话测试后再调整默认值。

SQLite 后端和离线导入工具已实现并可显式选择；默认仍为 JSONL。SQLite 可保护
本地并发事务。DSH 的连续会话快照与新服务已加入消息水位保护，但旧版 daemon、
无水位历史数据、fork/分叉以及投影删除均不受该保护；在端到端多进程部署验收前，
仍要求每实例使用独立目录。
数据库忙导致入队失败的 turn 会有界暂存在内存中重试，入库前进程崩溃仍会丢失。
会话持久化屏障最多重试 3 次；宿主无 durability listener、会话已 dispose 或仍失败
时改为告警后无屏障直发，避免队首阻塞后续归档（至少一次投递，服务端幂等兜底）。
真实 DSH 会话、目标文件系统验证
和生产迁移尚未完成，不能据此宣称已完成生产部署。
