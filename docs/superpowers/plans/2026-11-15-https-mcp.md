**Goal:** Enable authenticated HTTPS MCP access while preserving existing local clients and reliable session ingestion.

**Architecture:** A standard MCP Streamable HTTP server exposes business tools through an authenticated per-agent gateway. A local compatibility adapter maps existing UDS requests to the remote MCP service. TLS is provided by a documented reverse proxy, with the backend confined to a local socket. Preserve local queues and distinguish queued from committed.

**Spec:** `docs/superpowers/specs/2026-11-15-https-mcp-design.md`

**Constraints:** Single-user, shared-memory trust domain; no admin exposure; verify TLS; isolated tests only; preserve existing changes; no production deployment.

1. Inventory existing UDS method mappings, message framing and MCP tool semantics. Select and pin a compatible MCP SDK. Tests first for initialization, authorized tool discovery/calls, fixed agent identity, rejection of invalid tokens, permissions, Origin and oversized requests. Implement the local-only MCP backend and authentication.
2. Tests first for UDS adapter method/response mappings, fixed identity, TLS certificate verification, network errors and no admin access. Implement the adapter without introducing duplicate queues. Exercise real plugins using temporary sockets and isolated data.
3. Tests first for durable offline session ingest and checkpoint replay, ambiguous committed responses, stable IDs, queue exhaustion and permanent authentication errors. Adapt the existing queue path and validate no duplicate writes.
4. Add a reproducible Docker/Unraid deployment including GPU, TLS proxy, secrets, health checks, persistence and scheduling; document migration and rollback. Do not deploy.
5. Run focused integration/security tests and existing regression suites against isolated resources. Review all changes independently, request DeepSeek review, and report remaining target-host validation.
