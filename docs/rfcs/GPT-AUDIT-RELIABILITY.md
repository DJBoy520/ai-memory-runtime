# 外部审计意见（GPT，2026-11-08）— 规范性输入

> 本文件为审计原文逐字存档，是 RFC v3 的规范性输入。实施规格见 `RFC-AMR-RELIABILITY-FIXES.md`（v3）。
> 用户指令：先修写入一致性（阶段 A），再修模型加载（阶段 B），最后统一接口和观测（阶段 C）。

---

AMR 可靠性修复方案

## 一、目标与约束

目标是解决四类问题：
1. 写请求已经提交 SQLite，但因后续模型或 Qdrant 失败而向客户端报告失败。
2. 模型冷启动时，多请求重复等待、超时，后台任务反复失败。
3. 异步投影乱序、重试或崩溃后，Qdrant 可能被旧数据覆盖。
4. Agent 无法区分版本冲突、模型加载中、参数错误等业务状态。

约束：
- SQLite 保持记忆事实的唯一来源。
- 原生插件保留现有 80–300ms fail-open 预算。
- 现有 MCP 工具和客户端尽可能兼容；涉及返回语义变化的地方更新文档。
- 不自动合并记忆正文，不放宽 Agent 白名单。
- 实施前确认工作区状态，保留已有未提交修改。
- 不直接修改生产数据库或重启生产服务；先完成测试和迁移预演，再单独提交上线步骤。

## 二、阶段 A：修复写入与投影一致性（最高优先级）

### A1. 明确写入成功的含义

memory_create、memory_update、memory_delete 的同步路径只负责在同一 SQLite 事务内完成：
- 记忆主表和版本记录；
- 审计记录；
- 投影任务；
- 幂等记录及返回快照。

事务提交后立即返回，不在请求路径调用 embedding 或 Qdrant。返回中包含：

```json
{
  "memory_id": "mem_xxx",
  "version": 3,
  "projection_status": "pending"
}
```

pending 表示 SQLite 已提交、搜索投影尚未确认；不得将它解释为"写入失败"。`memory_get` 从 SQLite 读取，`memory_search` 仍查询 Qdrant，允许暂时读不到刚写入的数据。

### A2. 统一投影队列和写者

先盘点所有 Qdrant 写入入口，包括 v3、legacy、reconciliation、脚本和后台任务，形成生产者清单。未纳入统一顺序控制的写入入口不能宣称已实现单写者。

推荐采用一个规范队列；每条任务表达"某条记忆需要重新投影"，而不是要求 Worker 重放可能已经过时的局部快照：
- 处理时以 (collection, memory_id) 为投影键。
- Worker 读取 SQLite 中该记忆的最新完整状态，根据当前状态执行完整 upsert 或 delete。
- 引入独立的 projection_revision；任何影响投影的内容、状态或元数据变更都递增。不要使用仅在正文修改时递增的 version 充当投影版本。
- 同一投影键严格串行；第一版可限定单 Worker，并明确启动时防止第二个 Worker 同时消费。若要支持多 Worker，另行设计租约和 fencing，不在本次假定其安全。
- Worker 成功写入后，记录已投影 revision。若处理期间 SQLite 出现更新，必须保留或再次调度新 revision。
- Qdrant 写入成功、SQLite 标记完成前进程崩溃时，重试必须安全；因此保证的是至少一次投递、最终状态幂等，不是网络调用恰好一次。
- 重试采用退避；达到上限后进入可查询、可人工重放的死信状态。不能静默丢弃。

特别检查：`upsert → 元数据更新`、`upsert → delete`、同一正文版本的连续状态更新、不同 collection，以及写入过程中出现新更新。

### A3. 双队列迁移

qdrant_sync_queue 与 memory_projection_outbox 的切换要作为单独迁移步骤设计：
1. 统计旧队列各状态及所有生产者。
2. 明确停止旧写入、排水或迁移未完成任务的方式，以及切换屏障。
3. 新旧任务若可能操作同一投影键，必须经过同一串行投影器和 revision 规则。
4. 迁移需要可重复执行，并提供失败后的恢复步骤；不要直接删除旧队列或历史任务。
5. 测试旧任务延迟重试，确保不会覆盖新状态或复活已删除记录。

上线前以数据库副本演练迁移，输出任务数量和一致性对账结果。

### A4. 写接口幂等

为创建、更新、删除提供可选 idempotency_key，逐步让客户端重试时复用同一个 key。

在与业务写入相同的 SQLite 事务中保存：
- 幂等命名空间、操作名、key；
- 规范化请求摘要，包含目标、正文、状态、预期版本、collection 等影响结果的参数；
- 首次提交的响应快照及创建时间。

规则：
- 相同 key、相同请求摘要：重放首次提交结果，不重复创建、递增版本或新增投影任务。
- 相同 key、不同请求摘要：返回明确的幂等键冲突。
- 并发首次请求：数据库唯一约束保证只有一次提交，另一方读取并验证已有记录。
- create 的服务端生成 ID 必须包含在事务内保存的结果中。
- 明确 key 保留期限和过期后的行为。重放快照里的 pending 表示首次提交时的状态；当前投影状态通过独立查询获取。
- agent_id 是客户端声明的命名空间，不当作认证凭据。

## 三、阶段 B：修复模型冷启动

### B1. 跨线程、跨事件循环的单次加载

主事件循环和 Outbox Worker 的独立事件循环共享同一个 engine。使用线程安全的状态、锁和加载代次，确保同一时刻只有一个实际加载任务；不要跨事件循环直接共享 asyncio.Future。

要求设计并测试以下状态转换：加载、等待、失败、卸载、关闭、加载完成但结果已过期。加载线程先在局部变量中构造模型，只有代次仍有效时才挂载到 engine。

### B2. 分开请求预算和加载任务生命周期

- 请求等待达到自身预算时返回可重试的 MODEL_LOADING，不取消共享加载。
- 后台 watchdog 独立跟踪加载耗时，不能依赖仍有请求在等待。
- Python 线程卡死无法安全强杀：第一版应明确将服务标记为 unhealthy，并由受控的 systemd 重启机制恢复；如需进程隔离，单独设计。不要把 epoch 描述成能够终止卡住的线程。
- 配置加载等待、总体超时和启动预热，并记录实际加载耗时。
- idle_timeout_seconds <= 0 明确定义为禁用自动卸载；修改代码后才能配置为 0。

### B3. 保持插件延迟契约

插件继续按自身 80–300ms 预算 fail-open。模型未就绪时，本轮可以没有记忆上下文，但服务端应能报告 MODEL_LOADING 并继续后台加载。不要把预取请求的超时统一改成几十秒。

## 四、阶段 C：接口、状态和诊断

### C1. 稳定业务错误

在 JSON-RPC 边界返回稳定错误码及结构化数据，至少覆盖：

| 错误 | 客户端可用信息 |
| --- | --- |
| AGENT_UNAUTHORIZED | 请求的 Agent 标识 |
| VERSION_CONFLICT | memory ID、期望版本、当前版本 |
| MODEL_LOADING | 当前状态、建议重试时间 |
| QUEUE_FULL | 当前队列深度和上限 |
| INVALID_ARGUMENT | 错误字段与原因 |
| IDEMPOTENCY_CONFLICT | key 被不同请求复用 |

审查所有 `except ValueError`，确保领域异常不会提前被吞掉。通过真实 IPC 和 MCP 桥接往返测试错误码，而不只测试异常继承关系。

### C2. 统一状态

建立唯一的状态定义及兼容映射，先梳理 SQLite、Qdrant、legacy 接口和 reconciliation 的现有语义，再决定迁移：
- legacy archived、superseded 映射到标准状态时保留必要的替代关系。
- 重定向前检查原记录和目标记录的可见性、状态及作用域。
- 明确目标不存在、链环、跨项目和跨 collection 的行为。
- 迁移脚本先提供只读检查与统计，再提供可重复执行的迁移；在数据库副本上演练。

### C3. 基础可观测性

保留 journald，增加结构化字段和诊断命令：
- 每次请求生成服务端 request_id；客户端 ID 可作为关联字段，不直接假设全局唯一。
- SQLite 投影任务持久化关联 ID，使后台 Worker 能关联原始写请求；仅用 ContextVar 无法自动跨越持久队列和进程重启。
- 记录请求耗时、模型加载耗时、embedding 耗时、投影积压、最老任务年龄、失败和死信数量。
- amr doctor 输出服务、模型、SQLite、Qdrant、队列和最近分类错误；避免输出正文和凭据。

## 五、交付验收

zcode 完成后，应提供测试结果和迁移预演报告，至少覆盖：
1. 并发请求触发冷启动，模型只实际加载一次；请求超时不取消共享加载。
2. 加载线程永久卡住、迟到完成、卸载与关闭竞态都有确定行为。
3. SQLite 提交后模拟 Qdrant 不可用，写请求仍返回已提交且投影待完成。
4. 相同幂等键并发重试只产生一次业务提交；不同参数复用同一 key 返回冲突。
5. 测试投影乱序、元数据连续更新、删除后旧任务重试、Worker 在 Qdrant 成功后崩溃并恢复。
6. 投影 pending 时 memory_get 能读到最新事实；memory_search 的弱一致性在接口文档中明确说明。
7. 旧队列未完成任务和新队列同时存在时，最终 Qdrant 状态与 SQLite 一致。
8. IPC/MCP 客户端能收到可区分的业务错误码；原生插件保持既定 fail-open 时间预算。
9. 数据库副本上的迁移、回滚或恢复流程经过演练，并输出前后对账。
10. 给出上线顺序、服务重启步骤和回退条件；生产操作单独执行。
